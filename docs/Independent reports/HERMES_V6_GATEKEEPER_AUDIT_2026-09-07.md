## 1. THE CRITICAL LOOPHOLES

### Loophole A: The "Paper vs. Real" Margin Trap (Ref: Section 4)
* **The Plan's Flaw:** The plan states that the broker's 50% cash-equivalent rule for F&O margin *"constrains nothing in paper trading and is recorded here for the real-money gate only."*
* **The Reality:** If the paper trading engine allows 100% utilization of the Rs 8.71 lakh collateral for margin, but the live broker only allows Rs 3.55 lakh (due to the cash-equivalent limit), your paper performance will be a fantasy. Strategies built and backtested in paper mode will be instantly rejected by the live broker for insufficient funds.
* **The Fix:** The 50% cash-equivalent constraint **must** be enforced in the Phase 1 paper-trading simulation immediately. Paper must simulate live margin rejections.

### Loophole B: Database Migration Russian Roulette (Ref: L11 & Release 1A)
* **The Plan's Flaw:** Claude correctly notes that nobody knows which of the 10 migration files are active on the live Supabase database, proposing to *"build a real runner and a version table."*
* **The Reality:** Pointing a newly built migration runner at a database in an unknown state is highly dangerous and risks corrupting existing ledger data, creating duplicate tables, or dropping active columns. 
* **The Fix:** Mandate a **Schema Reconciliation Step (Release 0)**. The developer must pull the live Supabase schema, diff it against the codebase, baseline the current live state as `000_baseline.sql`, and *then* build the runner.

### Loophole C: Order Concurrency & Idempotency (Ref: Release 3)
* **The Plan's Flaw:** Release 3 covers limit vs. market simulation and charges but misses execution concurrency entirely.
* **The Reality:** If the UI lags and a user double-clicks "Execute Strategy" on a 4-leg structure, the frontend sends two identical API requests. Without idempotency, the system will fill 8 legs, doubling risk and blowing past the 5% Black-Swan fuse.
* **The Fix:** Every execution payload must carry a UUID idempotency key generated by the frontend. The backend database must reject duplicate keys within a 60-second window.

### Loophole D: The "Kill Switch" is Only a Pause Button (Ref: L7)
* **The Plan's Flaw:** The plan scopes the kill switch to *"Halt blocks risk-increasing actions only. Close, reduce... stay permitted."*
* **The Reality:** This is a "Pause" button. In a true black swan event or a partial-fill nightmare leaving the account naked short, blocking *new* trades is insufficient. Manual leg-by-leg closure loses precious seconds.
* **The Fix:** The Kill Switch must be **two-tiered**: 
  * *Tier 1 (Soft Halt):* Block new entries.
  * *Tier 2 (Hard Flatten):* Automatically cancel all open/pending orders and submit market orders to liquidate every open intraday position instantly.

### Loophole E: Fragility of the Risk Gate Data (Ref: Section 3)
* **The Plan's Flaw:** The risk scenario requires 20 complete sessions of NIFTY data with the strict rule: *"Any failure blocks. No substitute volatility, ever."*
* **The Reality:** This makes the terminal entirely dependent on a single API call returning perfect data. A temporary broker API glitch returning 19 days instead of 20 completely locks the user out of trading. 
* **The Fix:** Implement a sanctioned, read-only secondary fallback source (e.g., `yfinance` index data) strictly for the 20-session volatility calculation, or cache the previous day's successful calculation to survive brief API outages. The primary broker feed remains the source of truth once available.
